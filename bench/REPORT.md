# Candy v0.1.0 与 Lua 5.4 综合性能评估

> **注意：本报告是优化前的基线评估（旧版本）。** 优化后的实现、数据与结论见 [OPTIMIZATION.md](OPTIMIZATION.md)；旧图表已删除，最终对比图只保留在 `OPTIMIZATION.md`。

> 评估对象：当前工作区（优化前基线）
> 基准语言：PUC Lua 5.4.7（Homebrew，Apple Silicon 原生）
> 评估日期：2026-11-07

---

## 1. 结论摘要

**Candy 目前是一个处于早期原型阶段的 Lua 风格脚本语言，还不能作为 Lua 的通用替代品。**

在 Candy 已经实现的语法子集内（整数加减、比较、`if`、全局变量、函数定义与调用、递归），公平对比结果如下：

| 维度 | Candy 相对 Lua 5.4 | 结论 |
|---|---|---|
| 计算密集热代码（fib、整数加法） | **慢 1.37–1.45 倍** | 这是 Candy 目前最好的成绩 |
| 普通函数调用（非自递归） | **慢 2.2–2.9 倍**（对 Lua 全局函数 2.2–2.6 倍） | 调用路径是主要瓶颈之一 |
| 全局变量读写 | **慢 2.1–2.2 倍** | 全局表查找缺少内联缓存 |
| 编译 / 解析 | **慢约 1.6 倍** | 词法逐字符处理 + 常量不去重 |
| 进程启动 | **基本持平**（2.9 ms vs 2.8 ms） | Candy 的亮点 |
| 峰值内存（调用/全局密集程序） | **高约 3 倍** | 顺序代码中常量重复存储、vector 逐条扩容 |
| 峰值内存（常量唯一的编译负载） | **低约 48%** | 9 字节 Value 比 Lua 的 16 字节 TValue 更紧凑 |
| 最大递归深度 | **61 层 vs 约 499,000 层** | 固定 128 槽 VM 栈，差距约 8,180 倍 |
| GC | **不可用/不安全** | 跨 chunk 使用函数会段错误，无法评估 GC 性能 |

一句话总结：**在它支持的狭窄子集里，Candy 比 Lua 慢 1.4–2.6 倍；一旦涉及调用、全局访问、大规模代码或深递归，差距迅速扩大到数倍甚至数千倍。语言功能完整度和运行时健壮性与 Lua 不在同一阶段。**

同时也要看到几个积极信号：

- 采用 computed-goto 分发，指令格式仅 4 字节，Value 仅 9 字节，基础内存占用低于 Lua。
- 对**自递归**做了专门的 `CALLSELF` 指令优化，使 fib 只慢 1.37 倍；一旦改成普通全局调用，立即退化到 2.26 倍。
- 定义 10 万个函数仅慢 1.16 倍，说明分配器和解析器的吞吐并不差。
- 二进制和启动开销很小，具备嵌入式/轻量级场景的潜力。

但这些优点目前被语言特性缺失、GC 正确性问题和 VM 架构瓶颈掩盖。**如果目标是“与 Lua 竞争”，当前版本不具备可比性；如果目标是教学/嵌入式原型，它的底子不错。**

## 2. 测试环境与方法

### 2.1 环境

| 项目 | 值 |
|---|---|
| 机器 | Apple M2，8 核 |
| 系统 | macOS 26.6.2，Darwin 25.6.0（arm64） |
| Candy 编译器 | AppleClang 17.0.0，`-O3 -DNDEBUG` |
| Candy 构建 | CMake Release，`build-release/` |
| Lua | 5.4.7（Homebrew，`/opt/homebrew/bin/lua`） |
| 计时方式 | Python `time.perf_counter_ns()` 包裹整个子进程 |
| 采样 | 2 轮预热；每个用例 5–31 次；取中位数，同时记录标准差 |
| 扣除启动 | “净耗时” = 用例中位数 − 空脚本中位数（Candy 2.93 ms，Lua 2.75 ms） |
| 顺序 | 每轮交替 Candy/Lua 顺序，降低温度/调度偏差 |

### 2.2 公平性说明

- 两个语言执行**语义等价**的源码，输出逐字节校验一致。
- Lua 默认使用 `local function`（Lua 的最佳实践）；Candy 没有局部函数，只有全局 `def`。为了观察差距，另做了 Lua 全局函数版本和 Candy 自递归优化版本。
- Candy 的核心库在 CMake 中被显式加上 `-O3 -DNDEBUG`；Lua 使用 Homebrew 的发布构建。
- 所有结果都是**端到端进程时间**，包含进程创建、文件读取、解析、执行、退出。对耗时较长的用例，启动占比 < 3%；对短用例同时给出净耗时。
- 这些用例几乎不分配 Lua 对象。用 `collectgarbage("stop")` 关闭 Lua GC 后复测 fib/calls，时间不变（约 0.11 s / 0.02 s），因此差距不是 Lua GC 造成的。
- 测试只覆盖 Candy 当前能解析的语法。**不能**用 nbody、binary-trees、字符串/表操作等标准套件，因为 Candy 还没有循环、表、字符串操作和乘除法（见第 3 节）。

### 2.3 复现

```bash

cmake -S . -B build-release -DCMAKE_BUILD_TYPE=Release
cmake --build build-release -j8

# 2. 生成用例并运行
```

## 3. 功能覆盖：为什么“综合”对比受限

Candy 的解析器目前只实现了极小的语句/表达式集合（见 `src/core/candy_parser.c` 的 `_block` 与 `_expr`）：

| 特性 | Candy v0.1.0 | Lua 5.4 |
|---|---|---|
| 整数 `+`、`-`、`<` | ✅ | ✅ |
| 乘、除、取模、`==`、`~=`、`and/or` | ❌ 解析到但代码生成报错 | ✅ |
| `if` / `else` / `elseif` | 仅 `if ... end` | ✅ |
| `while` / `for` / `repeat` | ❌ | ✅ |
| 局部变量 | 仅函数参数；`local` 不是关键字 | ✅ |
| 函数 / 递归 | ✅（全局函数） | ✅ |
| 闭包 / upvalue | ❌ | ✅ |
| table / 数组 | ❌ | ✅ |
| 字符串操作 / 拼接 | 仅字面量与 `print` | ✅ |
| 标准库 | `print`、`exit` | 完整 |
| 元表 / 协程 / `pcall` | ❌ | ✅ |
| GC | 部分标记清除，chunk 结束时整轮执行 | 增量式 |
| 最大递归深度 | 61 | 约 499,000 |

因此，下文的“综合性能”应理解为：**Candy 已实现子集内的性能**。它不能代表 Candy 在表、字符串、闭包、循环、GC 压力下的表现——这些负载目前根本无法运行。

## 4. 运行时间结果

### 4.1 主要数据

“净耗时”已扣除空脚本启动时间；比值 > 1 表示 Candy 更慢。

| 用例 | Candy (ms) | Lua (ms) | 原始比值 | Candy 净 (ms) | Lua 净 (ms) | 净比值 |
|---|---:|---:|---:|---:|---:|---:|
| 空脚本（启动） | 2.9 | 2.8 | 1.06× | 0 | 0 | — |
| fib(30) 自递归 | 63.5 | 47.0 | 1.35× | 60.6 | 44.3 | **1.37×** |
| fib(34) 自递归 | 415.6 | 303.1 | 1.37× | 412.7 | 300.3 | **1.37×** |
| fib(30) 别名动态调用 | 112.5 | 51.3 | 2.19× | 109.5 | 48.6 | **2.26×** |
| fib(32) Lua 全局函数 | 161.8 | 130.7 | 1.24× | 158.9 | 128.0 | 1.24× |
| 40 万个调用点 | 121.7 | 47.9 | 2.54× | 118.8 | 45.2 | **2.63×** |
| 20 万调用（Lua 局部函数） | 62.7 | 23.6 | 2.65× | 59.8 | 20.9 | **2.86×** |
| 41 万次热调用（互递归） | 22.2 | 11.4 | 1.95× | 19.3 | 8.7 | **2.23×** |
| 40 万次全局读写 | 153.3 | 71.9 | 2.13× | 150.4 | 69.2 | **2.18×** |
| 40 万次整数加法 | 45.3 | 32.0 | 1.41× | 42.4 | 29.3 | **1.45×** |
| 编译 20 万行 | 79.4 | 49.9 | 1.59× | 76.5 | 47.2 | **1.62×** |
| 定义 10 万个函数 | 109.7 | 94.5 | 1.16× | 106.8 | 91.7 | **1.16×** |

几个关键观察：

1. **自递归是 Candy 的“舒适区”**：`fib` 只慢 1.37 倍，因为编译器把 `fib(...)` 编译成专门的 `CALLSELF`，跳过了全局函数查找。把递归目标改成另一个全局名 `fib2` 后，同样的计算变成 2.26 倍——这说明**普通调用的真实差距约为 2.2–2.9 倍**（对 Lua 全局函数约 2.2–2.6 倍，对 Lua 最佳实践的局部函数可达 2.9 倍），fib 的好成绩来自特化优化，而不是调用机制本身足够快。
2. **fib(34) 每次调用约 22.4 ns，Lua 约 16.3 ns**（按 18,454,929 次调用计算）。热调用场景下双方都能保持稳定，说明 CPU 频率和测量方法没有明显漂移。
3. **调用点和全局访问的比值随规模基本不变**（2.5–2.6 倍、2.1–2.2 倍），没有出现 GC 拐点，测试结果可信。
4. **纯加法只慢 1.45 倍**，是 Candy 最接近 Lua 的计算场景。

### 4.2 吞吐量

| 用例 | 工作量 | Candy | Lua | 比值 |
|---|---:|---:|---:|---:|
| 调用点吞吐 | 400,001 次 | 3.37 M/s | 8.86 M/s | 2.63× |
| 热调用（互递归） | 410,001 次 | 21.27 M/s | 47.36 M/s | 2.23× |
| 全局读写 | 400,000 次 | 2.66 M/s | 5.78 M/s | 2.17× |
| 整数加法 | 400,000 次 | 9.44 M/s | 13.66 M/s | 1.45× |
| 编译 | 200,000 行 | 2.62 M 行/s | 4.24 M 行/s | 1.62× |
| 函数定义 | 100,000 个 | 0.94 M/s | 1.09 M/s | 1.16× |

三条扩展曲线都近似线性，说明测试没有被缓存拐点或 GC 周期污染。

## 5. 内存结果

macOS `/usr/bin/time -l` 的 maximum resident set size（包含进程本身、编译器和运行时）：

| 用例 | Candy RSS | Lua RSS | Candy/Lua |
|---|---:|---:|---:|
| 空脚本 | 1.4 MB | 1.5 MB | 0.89× |
| fib(34) | 1.4 MB | 1.6 MB | 0.86× |
| 40 万次加法 | 6.7 MB | 8.0 MB | 0.84× |
| 编译 20 万行（常量唯一） | 13.6 MB | 26.0 MB | **0.52×** |
| 40 万个调用点 | 29.0 MB | 9.7 MB | **2.98×** |
| 40 万次全局读写 | 33.9 MB | 11.2 MB | **3.01×** |
| 定义 10 万个函数 | 118.8 MB | 42.7 MB | **2.78×** |

内存表现是“两个极端”：

- **基线、fib、加法、常量唯一的编译负载**：Candy 更省内存。原因是指令 4 字节、Value 9 字节，均小于 Lua 的 4 字节指令 + 16 字节 TValue；空进程基础占用也更低。
- **调用/全局密集、重复常量、函数定义**：Candy 反而高约 3 倍。主要原因是：
  - **常量完全不去重**：每个 `y = x + 1` 都会向常量池追加 `1`、名字 `x`、名字 `y` 三个 9 字节条目（`candy_proto_add_const` 直接 append）。
  - **vector 逐条扩容**：`candy_vector_append` 在容量不足时只把容量增加到“当前大小 + 1”（`candy_vector.h:87`），导致每次 append 都可能 `realloc`，没有几何增长预留，产生分配器开销和碎片。
  - **每个函数独立分配 proto + 两个 vector + closure + 名称对象**，10 万个函数时每次定义约 1.2 KB 常驻内存。

这也解释了为什么“编译 20 万行”反而比 Lua 省内存：该用例的每行常量都不同，Lua 需要保存大量 16 字节常量与常量表，而 Candy 的 9 字节紧凑 Value 占优；一旦常量重复（真实程序里很常见），Candy 的“不去重”就会放大 3 倍。

## 6. 规模化能力：递归深度

Candy 的 VM 栈在创建时固定为 **128 个槽位**（`CMakeLists.txt` 中的 `CANDY_CONFIG_VM_STACK_SIZE 128`），每个槽 9 字节。测试函数 `f(n)=1+f(n-1)`：

- `f(60)` 正常返回。
- `f(61)` 正常返回。
- `f(62)` 开始无法返回：**没有错误输出，退出码仍是 0**，表现为静默失败。
- Lua 在默认配置下实测可到 **499,218 层**才报 `stack overflow`（二分搜索到的最大确认值，实际上限可能略高，但低于 500,000）。

差距约 **8,180 倍**。这不是“慢一点”，而是**能力边界**：所有需要深递归的负载（解析器、AST 遍历、递归下降算法、树处理）在 Candy 上直接不可用。同时缺少尾调用优化，尾递归也会消耗栈。

## 7. 根因分析

### 7.1 栈式 VM 带来的指令放大

Candy 是操作数栈式 VM；Lua 5.4 是寄存器式 VM。以 `y = x + 1` 为例：

| | Candy | Lua |
|---|---|---|
| 指令 | `LOADG x`、`LOADC 1`、`ADD`、`SETG y` | `GETTABUP`、`ADDK`、`SETTABUP` |
| 指令数 | 4 | 3 |
| 每条 ADD 的栈操作 | 弹出 2 个、压入 1 个 | 寄存器直接相加 |

`a + a + ...` 的 40 万项链式表达式在 Candy 中编译为 40 万个 `LOADL a` + 40 万个 `ADD`；Lua 只需要 40 万个寄存器 `ADD`。这直接解释了 1.45 倍的加法差距，以及更大规模的调用/全局差距：**每个操作数都要先入栈**。

### 7.2 调用路径太重

每次脚本函数调用，Candy 都会：

1. 在 C 栈上构造一个 `vmll_t`（含 `candy_callinfo_t`、上下文、VM 指针等）；
2. `_callinfo_init` 计算 `bos/tos`；
3. `_call` 对被调值做类型 switch；
4. 进入 `_execute_proto` 的新 C 函数层；
5. 逐条执行被调函数的指令；
6. 返回时 `_op_return` 复制返回值、清空源槽；
7. `_vmll_deinit` 恢复调用者。

另外，`_vmll_push` / `_op_add` 等热路径上仍保留 `vmll_assert` 条件检查（`NDEBUG` 只去掉标准 `assert`，去不掉自定义的 `vmll_assert`）。对 400k 调用点、41 万热调用来说，这些固定开销被放大成 2.2–2.9 倍差距。

`CALLSELF` 通过跳过“取被调函数值 + 全局查找”把自递归成本压下来，但它只覆盖“函数直接调用自己”这一种模式；互递归、回调、别名调用都无法享受。

### 7.3 全局访问的多层间接

`LOADG` / `SETG` 的路径是：

```
candy_table_get / candy_table_set
  → _find
    → candy_wrap_hash(key)            // 通过 handler 函数指针回调
      → EVT_HASH → _array_hash
    → candy_map_find
      → 线性探测序列 {3,-3,5,-5,7,-7}
      → self->comp(...)               // 再次 hash + EVT_COMPARE 回调
```

每个全局访问至少经历两次函数指针回调和一次字符串哈希/比较。Lua 的 `GETTABUP` 使用 `_ENV` upvalue 和内联的 table 查找，字符串 hash 已缓存，路径短得多。这是 2.1–2.2 倍差距的主要原因。

### 7.4 常量与 vector

- `candy_proto_add_const` 只做 append，不做 hash-cons：相同的 `1`、`x`、`y` 在每条语句里都存一份（`candy_proto.c`）。
- `candy_vector_append` 的扩容策略是 `cap + size`，即容量正好等于元素个数，没有 1.5–2 倍的增长余量（`candy_vector.h:87`）。大文件编译时每次 append 都可能触发 `realloc`，这既增加分配器压力，也解释了 3 倍的内存峰值。
- 字符串常量有 interning（`candy_array_create_const`），但数字和名字常量没有。

### 7.5 词法/语法分析

- 词法器逐字符调用 `candy_buffer_view`，每个字符至少一次函数调用；标识符/数字通过 `_save_char` 逐字符 append 到缓冲区。
- 解析器在每次出现常量时做 interning 查找，并立即 append 到 proto 的 vector。
- 结果：2.5 MB 源码编译约 76 ms（Candy）vs 47 ms（Lua），慢 1.62 倍。考虑到 Candy 的功能远少于 Lua，这个成绩不算灾难，但仍有明显优化空间。

### 7.6 GC：不仅是性能问题，还是正确性问题

`candy_state.c` 在每个 chunk 执行完后调用 `candy_gc_full`，也就是说：

- **执行期间完全不回收**：单个 chunk 内分配的对象只能等 chunk 结束，长生命周期脚本会持续涨内存。
- **没有增量/分步回收**：Lua 的增量 GC 可以把停顿打散，Candy 是一次性全量扫描。
- **可达性遍历不完整**：`_table_color` / `_table_diffuse` / `_sclosure_color` 等 handler 都是空实现，GC 不会从全局表遍历到闭包/proto；这些对象在 chunk 结束时会被当成白色垃圾回收，但全局表仍保留悬空指针。

这不是理论问题。用 C API 连续执行两个 chunk：

```c
candy_dostring(s, "def f() return 42 end", ...);  // 返回 0，成功
candy_dostring(s, "print(f())", ...);             // 段错误（exit 139）
```

第一个 chunk 定义的函数在结束时被 GC 回收，第二个 chunk 再访问就是 use-after-free。**因此本报告不提供 GC 吞吐对比——Candy 的 GC 目前还不能安全地支撑跨 chunk 的运行时，谈“GC 性能”没有意义。** 这也是 REPL 和长驻服务场景的硬阻断。

### 7.7 Candy 做对的地方

- **computed-goto 分发**：`_execute_proto` 使用 `goto *dispatch_table[op]`，减少 switch 分支预测开销。
- **紧凑布局**：`candy_inst_t` 4 字节，`candy_wrap_t` 9 字节，基础 RSS 比 Lua 低约 11–16%。
- **`CALLSELF` 特化**：用一条指令覆盖自递归的“取函数 + 调用”，效果显著（fib 从 2.26 倍降到 1.37 倍）。
- **启动快**：空脚本 2.9 ms vs Lua 2.8 ms，二进制 + 动态库合计约 142 KB（Lua 约 322 KB）。
- **分配/解析吞吐不差**：10 万函数定义只慢 1.16 倍；常量唯一的编译负载内存反而只有 Lua 的一半。

## 8. 优化建议（按优先级）

### P0：先让语言“能跑完整程序”

1. **实现循环**：`while` / `for` / `repeat`；这是所有基准测试和真实程序的前提。
2. **实现 table/数组与字符串操作**（含 `..`、`#`、下标、方法调用）。
3. **补齐算术/逻辑/比较运算符**：`* / % == ~= and or`。
4. **修复 GC 可达性遍历**：table → key/value、closure → proto、upvalue；改为增量/分步回收，并在分配路径上触发，而不是 chunk 结束一次性扫描。
5. **动态栈 + 尾调用优化**：去掉 128 槽硬上限；栈溢出必须报错，不能静默退出。
6. **局部变量与闭包**：目前只有函数参数是局部变量，`local` 甚至不是关键字。

### P1：VM 性能（预计收益最大）

1. **寄存器化或融合指令**：把 `LOAD/LOAD/ADD/STORE` 融合成 `ADD R,A,B`、`GETGLOBAL R,K`、`CALL R,A,B` 等形式，消除操作数栈的 push/pop。参考 Lua 的 3 地址指令；预计算术/调用提升 1.5–2.5 倍。
2. **全局访问内联缓存**：每个 `LOADG/SETG` 站点缓存上次的 table slot 或键指针，命中时直接读写；未命中再走完整哈希。预计全局密集负载提升 1.3–2 倍。
3. **热路径去间接化**：
   - 把 `candy_vector_data/size` 的结果缓存在解释器局部变量；
   - `candy_wrap_hash` 直接对 interned 字符串读缓存 hash，避免 handler 函数指针；
   - 把 `vmll_assert` 的类型检查移到慢路径/调试构建。
4. **常量池 hash-cons**：数字、名字常量统一去重；配合 1.5–2 倍几何扩容，预计大代码内存降低 2–3 倍，编译时间降低 10–20%。
5. **Value 对齐**：9 字节的非对齐 8 字节读写属于未定义行为（ARM64 上通常可用但可能跨 cache line）。可改为 16 字节对齐的 tagged union，或采用 NaN-boxing 保持 8 字节。
6. **调用帧显式化**：用显式 frame 数组代替每次调用递归进入 `_execute_proto`，减少 C 栈和 `vmll_t` 构造；配合尾调用消除。

### P2：编译器与工程

1. **词法器批量扫描**：用指针直接扫描缓冲区，减少 `_view`/`_read` 函数调用；token 文本先指向源缓冲，最后再决定是否复制。
2. **解析器预分配**：按源码长度预估 instruction/constant 数量，`reserve` 一次，避免逐条 realloc。
3. **加入标准基准套件**：等循环/表/字符串/GC 就绪后，跑 nbody、binary-trees、spectral-norm、string/table 微基准、GC 压力测试；目前的结果不能外推到这些负载。

## 9. 综合判断

| 维度 | 评价 |
|---|---|
| **纯计算速度** | 约为 Lua 的 0.69–0.73 倍（慢 1.37–1.45 倍）；对原型 VM 来说不算差 |
| **函数调用** | 约为 Lua 的 0.35–0.45 倍；普通调用是明显短板 |
| **全局/表访问** | 约为 Lua 的 0.46 倍；缺少 inline cache |
| **编译速度** | 约为 Lua 的 0.62 倍；可接受，但有明确优化点 |
| **启动/体积** | 与 Lua 持平甚至更小；是优势 |
| **内存** | 基线更低，但大代码/调用密集场景约为 Lua 的 3 倍；两极分化 |
| **规模能力** | 递归 61 层、无循环、无表；与 Lua 不在一个量级 |
| **GC/健壮性** | 跨 chunk use-after-free；当前不可用于 REPL/长驻服务 |
| **功能完整度** | 约为 Lua 的 5–10%；标准基准套件无法运行 |

**最终结论：**

- 如果你的问题是“Candy 现在能不能替代 Lua？”——**不能**。在共同子集内它慢 1.4–2.9 倍，在规模能力上差数千倍，GC 还存在正确性缺陷。
- 如果你的问题是“Candy 的 VM 底子怎么样？”——**有一些可取之处**：computed-goto、紧凑 Value、自递归特化、低启动/低基线内存都说明作者理解 VM 的关键点；10 万函数定义只慢 1.16 倍也说明分配器并不差。
- 真正的差距主要不是“某条指令慢”，而是**架构选择**：栈式 VM 的指令放大、调用路径的固定开销、全局查找的多层间接、常量不去重、固定栈和缺失的 GC 遍历。这些都需要结构性改造，而不是微优化。
- 如果按 P0（功能 + GC + 动态栈）→ P1（寄存器/融合指令 + inline cache + 常量去重）的路线推进，**把计算/调用差距缩小到 1.2–1.5 倍是现实目标**；但要达到 Lua 的成熟度，仍需大量工程投入。

## 10. 局限与声明

1. **只覆盖 Candy 已实现的语法子集**。没有循环、表、字符串、闭包、乘除法，因此不能代表 Candy 在真实脚本负载下的综合性能，也不能外推到 Lua 的标准基准。
2. **Lua 版本为 PUC Lua 5.4.7**，不是 LuaJIT；LuaJIT 在数值/调用密集负载上会快一个数量级，但那不是本次对比对象。
3. **Candy 工作区有未提交修改**（`git status` 显示 parser/proto/vm 等文件被修改），结果对应本机当前工作树，不等于某个正式 release。
4. **调用点/全局读写/编译用例包含较大的顺序代码流**，受指令缓存、分配器和文件系统影响；热调用与 fib 更接近纯 VM 开销。这些影响对两个语言都存在，但代码密度不同会放大差异。
5. **峰值 RSS 是进程级指标**，包含解释器、编译器和运行时，不等于精确的堆统计；每个用例只测一次，适合看数量级，不适合看 KB 级差异。
6. **GC 性能未测**：Candy 的 GC 目前跨 chunk 不安全，任何“GC 吞吐”数字都不可信。这是正确性问题，已在第 7.6 节给出复现。
7. 机器为 Apple M2，结果可能与 x86-64、不同分配器、不同编译器版本有差异。
